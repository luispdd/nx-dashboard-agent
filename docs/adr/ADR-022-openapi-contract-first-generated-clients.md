# ADR-022: API Contracts — OpenAPI as Single Source of Truth with Generated Clients

## Status
Accepted

## Context
Maintaining API communication between an Angular frontend, a React micro frontend, a NestJS backend, and a Python FastAPI service can easily result in drift between frontend types and backend response models if contracts are hand-written.

Manually writing client SDKs, fetch wrappers, and TypeScript interfaces across polyglot repositories creates maintenance friction, silent schema mismatches, and broken runtime assumptions.

## Decision
We enforce **OpenAPI specifications as the strict contract between services** and require code-generation for consumer clients:

1. **Contract Generation**:
   - `dashboard-api` (NestJS) generates its OpenAPI specification from code annotations via `@nestjs/swagger` (`nx run dashboard-api:export-openapi`).
2. **Client Generation**:
   - Angular shell consumes the contract via generated services (`libs/shared-contracts` generated by `ng-openapi-gen` or custom signal-based resource generators via `nx run shared-contracts:generate-contracts`).
   - Python `agent-service` models its external tool types and payloads from the OpenAPI contract.
3. **No Editing Generated Files**:
   - Generated client files are never manually modified. Any contract adjustment starts at the source service, followed by spec re-export and client re-generation.

## Consequences & Verification
- **Zero API Drift**: Type changes in backend DTOs produce immediate compile-time errors in consumer frontends during `nx build` or `nx affected`.
- **Automated Validation**: CI verifies that OpenAPI specs and generated client libraries are up to date and in sync with backend code.
